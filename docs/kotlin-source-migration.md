# Replace the remaining handwritten Java with Kotlin

The simulator core and IntelliJ plugin already use Kotlin in production.
Finish the source migration across the CLI, X-Ray datapath, tests, benchmarks,
and examples. The completion criterion is zero tracked handwritten Java files.
JVM APIs and Java generated by Dagger or JMH remain part of the build where
those tools use them. The JMH annotation processor runs through kapt for the
benchmark source set. Keep language conversion commits separate from
instruction-set and runtime changes so the cause of any regression is easy to find.

## Rules for each stage

- Record the build and test baseline before moving a group. Compare discovered
  Jupiter cases and parameter invocations after the change. Preserve assertions,
  test resources, failure paths, and public JVM entry points that existing
  callers use.
- Use Kotlin's standard constructs where they preserve behavior. Use
  nullability, `use`, data classes, and SAM lambdas where appropriate. Keep
  explicit signed and unsigned conversions at assembly and register boundaries.
  Review collection ownership, overload resolution, checked exceptions
  visible to Java callers, and initialization order during each conversion.
  Keep general-purpose wrappers to the few cases that simplify several calls.
- Use one tested commit per stage or fixture group. Keep class/package names
  where build scripts, metadata, and external callers depend on them. Keep
  existing aggregate checks and coverage gates. Use the pinned Kotlin/JVM
  version and Java 25 toolchain already used by MARS.

## 1. Port the CLI and verify both archives

Convert [the CLI entry point](../mars5/cli/src/main/kotlin/edu/missouristate/mars/cli/MarsCli.kt)
and its three supporting classes. Retain the existing executable JAR main
class and public static `main` and `execute` contracts. Keep injected streams
for in-process invocations, and preserve option aliases, positional parsing,
diagnostics, dump and report formats, and exit status.

Run the existing CLI tests before converting them in a follow-up commit. Test
both the executable JAR and the assignment-definition JAR. The plugin's
smaller archive currently includes the compiled grading classes and
`HeadlessGuiProxy.class` by path. Confirm the Kotlin port still provides those
entries or update the packaging rules together with the port. Check the script
discovery marker and standalone grading, including arbitrary `.kts` filenames.
Re-run the IntelliJ registration test to cover the actual plugin classpath.
[CLI build and archive definitions](../mars5/cli/build.gradle.kts)

## 2. Port the X-Ray datapath tables

Enable Kotlin/JVM in [the datapath module](../mars5/datapath/build.gradle.kts).
Convert the records and static tables mechanically first. Preserve
[the diagram model's](../mars5/datapath/src/main/kotlin/edu/missouristate/mars/datapath/DatapathDiagram.kt)
defensive copies and immutable collection contract. Kotlin's read-only
collection types alone do not establish that contract.

Use the existing diagram test and compare all four sets of wires, links,
coordinates, palettes, and maps before and after conversion. Run the IntelliJ
X-Ray tests and inspect the built plugin for its expected JAR inventory.
Update the model and Kotlin consumers in the same commit if moving
record-style accessors to properties. Preserve JVM-facing entry points
where currently used by external callers.

## 3. Port the core tests in fixture groups

Work outward from shared fixtures such as `TestSessions` and
`TestEnvironment`. Keep callable signatures available to Java tests that have
yet to move. In later commits, remove interop glue introduced solely for those
tests once their last callers have migrated.

Suggested groups are register and memory state, instruction encoding and
semantics, assembler and pseudo-instructions, simulator and backstep, syscall
and settings isolation. Keep the largest integration suites in individual
commits when it makes the mapping from old to new assertions easier to review.
Verify expected test counts, including parameterized cases. Use Kotlin multiline
assembly literals where interpolation and whitespace are tested and preserved.
Check array and binary equality by content and confirm that JUnit invokes
Kotlin method sources, lifecycle hooks, and temporary-directory fixtures.

## 4. Run the JMH benchmark from Kotlin

Keep the existing JVM benchmark workload as the comparison point. The
[assembler benchmark](../mars5/core/src/benchmark/kotlin/edu/missouristate/mars/benchmark/AssemblerBenchmark.kt)
creates an isolated session and source file per trial, measures assembly of
10,000 instructions, and returns the assembled instruction count. Capture a
short baseline with the current JMH runner, then use the same settings and
workload during conversion. Put setup and teardown outside the measured path.

Write the workload as an ordinary Kotlin benchmark method and keep upstream
JMH as the Java dependency. Wire its generator for the Kotlin benchmark source
set and retain the existing Gradle task entry points. Check that Kotlin
classes and methods have the visibility and openness required by generated
JMH subclasses. Verify that a clean build generates benchmark metadata,
JMH discovers the workload, the benchmark process exits normally, and JMH
can write its standard results. [OpenJDK JMH][jmh]

The existing workload can return the instruction count directly. Use JMH's
own Blackhole if a later workload needs to consume multiple results. Use
JMH's standard reporting formats. Keep the benchmark smoke run separate
from pass/fail performance thresholds.

## 5. Port the smoke programs and qualify the full build

Convert the instruction-lab launcher and both projects' tests in the
[standalone smoke build](../examples/smoke/settings.gradle.kts). Keep its
composite build import, CLI launch behavior, generated inputs, and expected
results. Preserve the PNG test's expected pixels and the instruction lab's
catalog coverage. Run the smoke build independently of the main build.
Verify the Kotlin benchmark still compiles on the CI paths that already build
`benchmarkClasses`.

Finish with a clean main build, CLI archive tests, smoke-project checks,
benchmark discovery and a short JMH run, Plugin Verifier, and the existing
packaged IntelliJ smoke workflow on the pinned IDE. Check that IDE imports work
for both builds and that no handwritten `.java` files remain in
`git ls-files`. Review which Gradle Java configuration still serves JVM
artifacts, source sets, or generated code before removing any build logic.
